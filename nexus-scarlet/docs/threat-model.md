# NEXUS Threat Model (Raven Security Foundation)

## 1. System Overview
NEXUS is an evidence-driven, security-first bug intelligence platform built to reconstruct and secure the workflows historically managed by Bugzilla. It handles bug tracking, vulnerability reporting, and automated threat analysis (powered by Cipher). Because NEXUS handles highly sensitive zero-day security reports, its design must assume a hostile operating environment.

> [!NOTE]
> **Implementation Scope & Integration**: Standalone security controls (RBAC permission engine, input validation schemas, and Secret Sentinel heuristic scanner) are fully **IMPLEMENTED** and **PASSING**. Initial authorization middleware (`checkPermission`), Helmet header configurations, and database query bindings are integrated into the Issue API (`src/issues/routes.ts`). Integration tests for headers, input/storage XSS boundaries, SQL injection parameters, and route RBAC blocks are written in `tests/security/` using Vitest and Supertest.

## 2. Assets
- **`user_identity`**: Credentials, session tokens, passwords.
- **`roles`**: User roles and permission configurations.
- **`issues` / `private_issues`**: Standard bug tracking records and restricted zero-day security bug reports.
- **`comments`**: Thread discussions under issue reports.
- **`attachments`**: Files uploaded by users (e.g. PoCs, logs, screenshots).
- **`secrets`**: API keys, credentials, or keys leaked within comments or issue details.
- **`security_findings`**: Automated scan logs generated by Secret Sentinel or vulnerability checkers.
- **`ai_analysis`**: Analytical outputs generated by Cipher on issue files.
- **`audit_logs`**: System audit trails tracking actions, logins, and configurations.
- **`release_information`**: Internal patches, security advisories, and code integrations.
- **`notifications`**: Email messages, notifications, and alert queues.

## 3. Actors
- **`Anonymous Visitor`**: Unauthenticated client. Can view public issues if allowed, but should have no write/private access.
- **`Viewer`**: Stakeholder with read-only access.
- **`Developer`**: Engineer creating, triaging, and fixing bugs.
- **`Project Manager`**: Admin-lite managing project scope, keywords, and schedules.
- **`Security Reviewer`**: Security auditor authorized to see vulnerabilities and audit findings.
- **`Administrator`**: Full system controller.
- **`Malicious Actor`**: Internal or external adversary attempting data extraction or bypass.

## 4. Trust Boundaries
- **`Client-Server Boundary`**: Separates client browsers (untrusted) from NEXUS APIs (trusted).
- **`Database Boundary`**: Separates the application engine from the persistent storage layer.
- **`Process Boundary (AI Engine)`**: Separates the core backend from Cipher's AI processing workers.
- **`Authentication Boundary`**: Separates anonymous users from authenticated users.
- **`Role Boundary`**: Delineates different authorization clearance levels (e.g. Viewer vs Admin).

## 5. Entry Points
- `/api/auth/*` (Login, session validation, OAuth login)
- `/api/issues/*` (Create, update, search, export issues)
- `/api/attachments/*` (File uploading and downloading)
- `/api/comments/*` (Posting discussion threads)
- `/api/notifications/*` (Queue triggers, webhooks)

## 6. Threat Analysis & Attack Scenarios

### Threat 1: Authentication Bypass / Identity Confusion
* **Attack Scenario**: An attacker manipulates JWT payloads or session cookies to log in as another user without credentials.
* **Asset Affected**: `user_identity`, `roles`, `private_issues`.
* **Security Boundary**: Authentication Boundary / Client-Server Boundary.
* **NEXUS Control**: Cryptographically signed, HTTP-only, secure, SameSite session cookies. Explicit token signature verification.
* **Planned Test**: `tests/security/auth/auth.test.js`
* **Status**: `DEFINED + BLOCKED BY BACKEND` (Upstream session validation middleware is not yet implemented by Scarlet).

### Threat 2: Unicode Identity Confusion (Homograph Attack)
* **Attack Scenario**: Attacker registers a user named `аdmin` (using Cyrillic 'а' U+0430) to confuse reviewers and mimic the real `admin` (using Latin 'a' U+0061).
* **Asset Affected**: `user_identity`, `audit_logs`.
* **Security Boundary**: Authentication Boundary.
* **NEXUS Control**: Rigid input validation pattern checks matching only Latin-ASCII alphabets for usernames, or NFKD normalization checks.
* **Planned Test**: `tests/security/validation/validation.test.js`
* **Status**: `IMPLEMENTED + PASSING` (Strict regex check and space validation are enforced in Raven's standalone validation engine).

### Threat 3: Cross-Site Scripting (XSS)
* **Attack Scenario**: Attacker submits a comment or issue title containing `<script>alert(1)</script>` which runs in other users' browsers.
* **Asset Affected**: `user_identity` (session hijacking), browser client context.
* **Security Boundary**: Client-Server Boundary.
* **NEXUS Control**: Escaping/encoding on output rendering in the browser, markdown sanitization in the client sandbox, and strict CSP headers.
* **Planned Test**: `tests/security/xss.test.ts`
* **Status**: `DEFINED + BLOCKED BY TEST ENVIRONMENT` (Input and storage boundary checks are written to verify raw payloads persist literally. Browser-side rendering defense is `DEFINED + BLOCKED BY FRONTEND`).

### Threat 4: Cross-Site Request Forgery (CSRF)
* **Attack Scenario**: Attacker tricks a logged-in admin into clicking a link that triggers an automatic POST to `/api/issues/123/update` to change the issue status or assign it to the attacker.
* **Asset Affected**: `issues`, `roles`.
* **Security Boundary**: Client-Server Boundary.
* **NEXUS Control**: Custom request headers (e.g. `X-CSRF-Token`) validated server-side, and SameSite=Strict cookies.
* **Planned Test**: `tests/security/csrf/csrf.test.js`
* **Status**: `DEFINED + BLOCKED BY BACKEND` (Upstream CSRF middleware is not yet implemented by Scarlet).

### Threat 5: SQL Injection (SQLi)
* **Attack Scenario**: Attacker inputs `1' OR '1'='1` in the issue search field, causing the database to bypass filters and return all private issues.
* **Asset Affected**: `issues`, `private_issues`, database credentials.
* **Security Boundary**: Database Boundary.
* **NEXUS Control**: Parameterized raw SQL queries executing via pg pool positional arguments.
* **Planned Test**: `tests/security/sqli.test.ts`
* **Status**: `DEFINED + BLOCKED BY TEST ENVIRONMENT` (Tests exercise real database paths and parameters, and skip dynamically if PostgreSQL is unreachable).

### Threat 6: Private-Data Disclosure (Query Leakage)
* **Attack Scenario**: Attacker sends a query that traverses dependency graphs to fetch bug metadata linked to a private security bug they are not authorized to view.
* **Asset Affected**: `private_issues`.
* **Security Boundary**: Role Boundary.
* **NEXUS Control**: Server-side RBAC validation enforced on graph endpoints and nested resources. 
* **Planned Test**: `tests/security/privacy/privacy.test.js`
* **Status**: `TEAM DECISION REQUIRED` (Undecided privacy classification policy; private issue logic remains undefined).

### Threat 7: RBAC/Authorization Bypass
* **Attack Scenario**: A `VIEWER` edits the HTTP POST payload to send a bug update request to `/api/issues/101`, bypassing frontend restrictions.
* **Asset Affected**: `issues`, `private_issues`.
* **Security Boundary**: Role Boundary.
* **NEXUS Control**: Server-side RBAC validation (`checkPermission`) on all Issue API routes.
* **Planned Test**: `tests/security/rbac-integration.test.ts`
* **Status**: `IMPLEMENTED + PASSING` (Enforces correct 401/403 blocks based on upstream user role context).

### Threat 8: Malicious Attachments
* **Attack Scenario**: Attacker uploads a PHP script disguised as an image (`shell.php.png`) or a script that causes remote code execution on the hosting server.
* **Asset Affected**: Server filesystem, server process execution.
* **Security Boundary**: Client-Server Boundary / OS filesystem.
* **NEXUS Control**: Whitelist MIME types, strict filename regex checks to block path traversals (`^[^\\\/:*?"<>|]+$`), and size limits (max 10MB).
* **Planned Test**: `tests/security/attachments/attachments.test.js`
* **Status**: `DEFINED + BLOCKED BY BACKEND` (Upstream file upload routing and physical storage directories are not yet implemented).

### Threat 9: Unsafe Content Rendering (Sniffing)
* **Attack Scenario**: Attacker uploads an HTML file with embedded javascript. When other users click the attachment link, the browser renders it as HTML, executing the script.
* **Asset Affected**: `user_identity`, client browser context.
* **Security Boundary**: Client-Server Boundary.
* **NEXUS Control**: Enforcing `Content-Disposition: attachment` headers, `X-Content-Type-Options: nosniff` (set via Helmet), and separate domain storage origins.
* **Planned Test**: `tests/security/headers.test.ts`
* **Status**: `IMPLEMENTED + PASSING` (Verifies Helmet configurations are active on the application HTTP ports).

### Threat 10: Secret Leakage in Issues/Comments
* **Attack Scenario**: A developer accidentally pastes a live API key or database password into a bug comment.
* **Asset Affected**: `secrets` (compromised external systems/databases).
* **Security Boundary**: Client-Server Boundary.
* **NEXUS Control**: Secret Sentinel regex-based scanner intercepts inputs and flags potential secrets before persistence.
* **Planned Test**: `tests/security/secrets/secrets.test.js`
* **Status**: `IMPLEMENTED + PASSING` (Regex rules and redaction logic pass standalone verification).

### Threat 11: Email/Notification Injection (CRLF)
* **Attack Scenario**: Attacker injects `\r\nBcc: victim@example.com` into the subject line of an issue, causing the mail server to send copies of private bugs to external addresses.
* **Asset Affected**: `notifications`, `private_issues`.
* **Security Boundary**: Client-Server Boundary / SMTP connection.
* **NEXUS Control**: Strict input validation stripping CRLF characters (`\r`, `\n`) from email subject lines and header fields.
* **Planned Test**: `tests/security/notifications/notifications.test.js`
* **Status**: `DEFINED + BLOCKED BY BACKEND` (SMTP routes and notification mailers are not yet implemented by Scarlet).

### Threat 12: Notification Failure (Silent Failures)
* **Attack Scenario**: A critical security bug is created, but the notification queue silently crashes, leaving security reviewers unaware of the vulnerability.
* **Asset Affected**: `notifications`, `private_issues`.
* **Security Boundary**: Core process to queue process.
* **NEXUS Control**: Persistent outbox pattern or transactional message queue with retry logic and alert monitoring.
* **Planned Test**: `tests/security/notifications/notifications.test.js`
* **Status**: `DEFINED + BLOCKED BY BACKEND` (SMTP outboxes and transactional message brokers are not yet implemented by Scarlet).

## 7. Assumptions
- The database host is configured securely and only accepts connections from the NEXUS core backend process.
- The operating system disables script execution (e.g. PHP/Node execution) on folders dedicated to user attachments.
- Session cookie secrets are stored in environment variables, rotated, and never hardcoded in the repository.

## 8. Residual Risks
- **Zero-day browser vulnerabilities**: A client browser vulnerability could bypass CSP protections.
- **Social Engineering**: Users with valid roles (e.g. `SECURITY_REVIEWER`) leaking private bugs manually.
- **AI Hallucinations**: Cipher could make false assertions about security levels, requiring human oversight.
